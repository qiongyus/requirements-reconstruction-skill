# 多轮重建规划（大型项目）

本文件展开 SKILL.md「产出分级与规模纪律」的规模警戒条款：当行为面总量远超单轮容量（经验阈值：估计行为面 > 100，或标准档以上整项目）时，如何把重建切成多轮、按什么顺序推进、以及与 `architecture-reconstruction` 的 AD 如何衔接。单轮能盘完的项目不需要本文件。

依据标注沿用本 skill 惯例：【一手】= 有出处可查证；【工程判断】= 从既有规则外推的综合，附推理但无标准背书，参数待多项目实测校准。

## 一、三层结构

多轮规划分三层，各管一个维度，不可互相替代：

| 层 | 职责 | 用什么 |
|---|---|---|
| **调度层** | 定轮次的语义边界与顺序 | 领域概念 / 架构视角（AD 存在时直接用它，见第三节） |
| **清点层** | 保证轮内不漏 | 十类行为面清单 + 八问盘问集（`behavior-surface-checklist.md`），照常执行 |
| **定量层** | 封顶轮次大小 | 共享探针台架 + 治理带宽（见下） |

**分层的理由**：概念/视角模型负责「圈地」，但静默契约（stdout/stderr 流向、信号处理、空响应体这类没人有意设计的行为）不住在概念模型里——只有清点层的机械枚举能抓到它们。调度层告诉你发现归档到哪，不负责找到它。【工程判断，推理见上；反例检验：纯概念驱动的轮次永远调度不出「盘问启动期 stderr」这个任务】

### 一之二、何时切到构建驱动开发（调度层的替代方案）

本文件的调度层沿**领域概念/架构视角**聚类，目标是需求覆盖完备。存在构建环节时还有另一种调度层：**沿可运行增量聚类**——由 `construction-driven-development` skill 编排（主干 + 现成项目条件规则 + 对等重写特化；其对等特化即原 `construction-driven-rewrite`，2026-08-11 改组吸收）。清点层与定量层两者共用，**只有调度层不同**。

| 情形 | 用哪个调度层 |
|---|---|
| 只补 spec 文档、不重建实现 | **本文件**（概念驱动）。没有构建环节，增量无从谈起 |
| 对等重写或重设计，但项目小到单轮或两三轮能盘完 | **本文件**。增量循环的台架与账本开销摊不薄 |
| 对等重写，行为面数百条，且**源项目有可跑的端到端测试套件** | **切到 `construction-driven-development`**（激活对等特化）：从上游测试锚点推导增量，边建边补需求 |
| 重设计（部分行为有意改变）且要重建实现 | **切到 `construction-driven-development`**（主干 + 条件规则）：全局清点照做，逐行处置标注（保留对等/有意改变/弃/显式未决）作分流开关，改的面由新 spec 裁判、保留面仍可用对照验收 |
| 对等重写，行为面很多，但源项目**没有可用测试套件** | 先按本文件推进；构建驱动降级为「自造探针锚」后仍可用，但失去上游裁判的权威性，收益大减 |

**切过去会得到什么**：构建启动不必等需求全部重建完（实测对照：概念驱动排序下第一个可运行增量要等到第 6 轮量级；增量切分下首轮即可构建）；每轮有实车 parity 对照，取证错误当轮暴露而非集中到实现阶段；构建中发现的行为差异有反哺回需求层的通道。

**切过去要付出什么**：必须同时接受三个防护——全局侦察与覆盖率账本、奠基轮的横切概念前置、账本收敛条件。**裁掉任何一个都会劣于本文件的概念驱动多轮**（实测：无 skill 的基线规划会把三个全裁掉，理由听起来都很合理）。付不起这三项开销就留在本文件。

**衔接方式**：已按本文件跑完的轮次产出（矩阵、发现清单、已导入块、探针脚本）**全部继承**；本文件第五节的多轮五纪律原样继续适用；轮次表转为增量计划，本文件保留为概念地图与候选池播种来源，不再滚动维护轮次状态。

## 二、轮的定义（颗粒度）

一轮 = **行为面聚类 × 共享探针台架 × 治理带宽**，外加一条机械约束。

1. **语义边界——沿概念/视角聚类,不沿代码模块**。代码边界与契约边界不重合（典型:retention 类行为实现在存储库、契约表现横跨全部摄入协议）。跨面对照类发现（如「两个端点对同类错误语义相反」）只在同轮才浮得出来,所以**共享同一领域概念的行为面归同轮**。【一手,SKILL.md「聚类约定」的多轮外推】
2. **成本边界——共享探针台架的行为面捆进同一轮**。探针是强制成本（「验证:不要停在纸上」),台架（构建基线二进制、起实例、备语料）是固定成本,同台架摊薄;且同台架 = 同构建同环境,探针结果才相互可比。概念太大横跨多套台架时,按台架拆子轮。【工程判断】
3. **数量上限——治理带宽**。人工裁决是管线的契约性串行环节（accept 与 blocking 答复都必须人做,【一手,agent-spec README「human governance action」】）。经验参数:**每轮 5–15 块、blocking 问题 ≤20 条**,超出即拆轮。比率参考:实测约每块产生 1–2 条 blocking。【工程判断,由 chmln/sd 与 VictoriaLogs 两次实跑校准,当可调参数用】
4. **机械约束——每轮依赖闭合**。门 3（`graph --gate`）不允许悬空依赖:一轮的块只能依赖同轮的块或已导入 `knowledge/` 的块。被依赖的面所在的轮必须先跑。【一手,门 3 实测行为】

超过带宽上限的处理是拆轮,不是压缩纪律——批量生成未过探针的断言比少产几块更糟（见 SKILL.md 三个失败模式）。

## 三、与 architecture-reconstruction 的衔接

`architecture-reconstruction` 的 AD（默认 R&W 七视角,【一手,该 skill SKILL.md Step 3】）是现成的调度层:Context 视角给外部依赖方清单（= parity 风险的定义域与 Hyrum 依赖证据来源）、Functional/Information 视角给功能元素 DAG 与横切概念、Concurrency/Deployment/Operational 视角认领概念模型之外的孤儿行为面、契约缺口清单直接作各轮的发现种子。

**硬纪律:AD 只作调度输入,不作需求证据。** AD 的断言是带置信度的逆向产物;拿它定轮次边界是安全的（调度错了重切即可）,但**不得进入任何需求块的 `## Source Trace` 或 `confidence`**——各轮取证必须重新钉到源码/测试/文档的 `file:line`。AD 给出的证据位置可作矩阵种子,升格【事实】前逐条重验。

两条增益用法:AD 的缺口/弱点清单指到哪里,对应轮的探针就加密到哪里（AD 自认「未实测」的推断,由需求轮的探针顺带验收）;需求轮的发现反向回填 AD（静默契约常暴露架构图上没画的耦合）——战役期间 AD 是活文档。

基线要求:AD 与全部需求轮钉同一基线。AD 基线不同则先重定或做差异报告,不许混用。

## 四、排序依据

| 序 | 依据 | 说明 |
|---|---|---|
| 1 | **裁决杠杆前置** | Open Questions 会改变重写总体形状的轮最先跑（典型:「是否保库 API 兼容」「是否读旧磁盘数据」）。裁出「否」即整体豁免大片后续清点——先问省得多 |
| 2 | **横切概念第二** | 被所有后续条款引用的概念（租户、时间、错误语义）先入库,门 3 依赖闭合也强制这个次序 |
| 3 | **体量主体跟随实现顺序** | 真相层只需跑在重写实现前一步,不必全部重建完才动工;每个 work unit 起草 contract 前其需求已 accept 是唯一同步点 |
| 4 | **台架成本殿后** | 需要多实例/故障注入的轮排最后,且尽量复用前面轮已裁定的语义作对照基线 |
| 5 | **并行许可** | 无依赖关系且 id 已分段的轮可多会话并行;共享台架的轮组（如查询语言各家族）并行收益最大 |

轮内排序沿用发现清单的判据:「重写时静默破坏的代价」大者优先。【工程判断,1–4 的权重无标准背书】

## 五、多轮特有纪律

- **基线钉死**:全部轮次同一 commit,战役期间不追新;结束后一次显式重定基线 + 差异报告。上游改动快的项目（看 AD 演进视角的变更热度）这条尤其硬。
- **id 命名空间预分段**:`requirements import` **不查跨文件重复 id**（【一手,`cli-gates.md` 门 1 实测】）,并行轮撞 id 不会被拦。规划时按轮分配前缀段（`REQ-<概念>-*`）,写进轮次计划。
- **已导入块不重复 import**:后续轮扩展既有主题时新开 id 并声明 `Dependencies`;改写既有块走 `requirements transition`/`supersede`,不覆盖导入。
- **每轮独立验收**:三件套（矩阵增量、发现清单、候选块）→ 四道门 → blocking 收敛 → 人工 accept。不允许「攒几轮一起过门」。
- **访谈攒批**:上游维护者少（巴士因子低）的项目,blocking 问题跨轮合并去重、分主题成批提问,不逐轮打扰。

## 六、轮次计划文档的必备结构

多轮启动前先落一份 `rounds-plan.md`（与三件套同目录）,按此七段写:

1. **头部**:源项目、基线、分流、调度依据（AD 路径 + 「AD 只作调度输入」声明）;
2. **全局纪律**:基线、id 分段表、已导入块清单、治理带宽参数;
3. **轮次总表**:每轮一行——名称、id 段、视角/概念来源、预计块数、依赖轮、台架;
4. **各轮细则**:范围、调度输入播种的发现/缺口、预告的裁决问题;
5. **排序依据**:按第四节五条写明本项目的具体理由,可审计;
6. **完备性互查**:调度输入的缺口清单 × 轮、十类行为面 × 轮,两张表都不许有孤儿——挂不到任何轮的新行为面回本计划加轮,不塞进不相干的轮;
7. **范围外声明**:显式列出不做的部分及理由（与覆盖率声明同一纪律:不许靠沉默）。

## 七、状态与校准

本文件的三层结构、颗粒度三因子、排序权重属【工程判断】,由两次实跑（chmln/sd 单轮 dogfood、VictoriaLogs 多轮规划）提炼,尚未经完整多轮战役检验。可检验预言:按概念/视角切的轮,其 blocking 问题比按台架切的更同质、更好裁——多轮实测后按结果修订本文件,预言不成立就改切法。
