# 证据源分类与置信度判据

本文件是 SKILL.md「证据纪律」一节的细则展开：八类证据源各自的能力边界与陷阱、证据类别组合到 confidence 的推导表、三源冲突的处理规则、Source Trace 钉版本的硬要求。三级标注体系、证据类别组合写法本身、Source Trace 的基本格式已在 SKILL.md 定义，此处不重复，只给判据。

## 一、8 类证据源

对应 `scripts/inventory_behavior_evidence.sh` 清点的 8 类行为证据源。逐类给出：能证明什么 / 不能证明什么 / 已知陷阱。脚本报告某类证据源不存在时，该类别对应的「能证明什么」在这个项目上不成立——据此决定哪些结论根本没有依据可给，不要绕过去凭印象补。

### 1. 分层测试（unit/integration/e2e/golden/快照）

- **能证明什么**：某行为被**有意锁定**——有人特意写下断言，是最接近「意图」的证据源。
- **不能证明什么**：断言本身不能证明它锁定的是**外部可观察行为**（可能是内部状态）；也不能证明被锁定的细节是设计意图而非偶然（golden/快照测试尤其如此）。
- **已知陷阱**：
  - 单元测试常断言内部状态、私有字段、调用次数——不可直译，闸门判据见 SKILL.md「测试直译判据（场景层的粒度闸门）」，此处不重复列举。
  - golden/快照测试容易把格式细节等偶然行为固化成「契约」（发现 #4：测试锁死的偶然行为）——"有测试锁定"不等于"是设计意图"，必须先过 parity 分类闸门再决定是否进场景。

### 2. 可执行示例（examples/、文档中的可运行代码块）

- **能证明什么**：这种调用方式在编写时是可运行的；若被 CI 实际执行，具有随代码演进保持有效的时效性保证。
- **不能证明什么**：不能证明这是唯一支持的用法，也不能证明未覆盖的分支（错误路径、边界值）的行为。
- **已知陷阱**：不在 CI 里执行的示例可能已经过时而不自知——用前先确认它是否被测试框架实际跑过；跑不过的示例，证据地位应降级，按 doc-only 处理，不能当作 code-verified 的行为证据。

### 3. API schema（openapi/proto/jsonschema）

- **能证明什么**：接口公开面的结构性声明——字段名、类型、是否必填、取值约束；常是生成代码或校验逻辑的输入，机械约束力强。
- **不能证明什么**：schema 声明的约束不代表实现真的强制执行了它（例如声明必填但代码未校验）；也不能证明字段的语义（为什么存在、如何使用）。
- **已知陷阱**：手写 schema 或生成代码未随实现更新会漂移；必须与实现里的序列化/校验逻辑对照，不能单独采信 schema 文件。

### 4. CLI help/man

- **能证明什么**：命令行面公开声明的子命令、标志、默认值文本；若由代码里的 flag 定义自动生成，机械性强，是行为面清点的高性价比起点。
- **不能证明什么**：帮助文本里的默认值/说明不保证与解析逻辑完全一致；不能证明不存在未文档化的隐藏标志。
- **已知陷阱**：手写（非自动生成）的 help 文本与 flag 解析代码分离维护，同样存在漂移风险，需与解析代码核对，不能只读文本就下结论。

### 5. 用户文档（README、docs/、教程）

- **能证明什么**：项目对外**宣称**的行为——对外承诺，这正是「文档」这一证据源要回答的问题。
- **不能证明什么**：不能证明宣称的行为已被实现（可能正是发现 #1：文档承诺未实现/与实现相反）；不能证明它是当前版本的准确描述。
- **已知陷阱**：用户文档天然只写收益，边界情况、失败路径、限制通常缺失，覆盖面系统性偏窄；且文档随代码演进可能已漂移（发现 #1）——必须以代码行为核实，核实不了则维持【缺口】，不得直接采信宣称内容写成条款。

### 6. CHANGELOG

- **能证明什么**：某版本确实发生过的变更事实（what changed），有时可佐证某行为的引入/移除时点，帮助判断行为的历史稳定性。
- **不能证明什么**：不能证明变更的动机（why）——CHANGELOG 描述 what 不含 why，rationale 恒为【缺口】，同 architecture-reconstruction 关于决策理由不可从代码/变更记录恢复的结论。
- **已知陷阱**：条目粒度不一致，内部重构或未被特意记录的行为改动会遗漏；不能仅凭「CHANGELOG 没提」就断定某行为在该版本区间未变。

### 7. 上游兼容套件

- **能证明什么**：若项目自带面向其他实现的兼容性/一致性测试套件，它标出了「哪些行为被明确当作跨实现契约」——比普通测试更强的意图信号，接近 semver 公开面承诺。
- **不能证明什么**：套件覆盖之外的行为没有任何保证；套件本身可能不完整，或滞后于协议/格式的最新演进。
- **已知陷阱**：容易被误当成「全部公开契约」的清单，实际它往往只覆盖被显式测试驱动的子集——未被套件覆盖不代表不是契约，只代表这里拿不到直接证据，仍需走其他证据源核实。

### 8. issue / 讨论区

- **能证明什么**：下游使用者是否在依赖某个行为——这是 `parity-incidental-relied` 判据里「依赖证据」（下游 issue、生态用法、兼容性讨论）的**唯一来源**。
- **不能证明什么**：讨论的存在不代表项目维护者认可或承诺了该行为；单条 issue 不构成「广泛依赖」的证明，需要判断依赖的广度与严肃程度。
- **已知陷阱**：这类证据本地仓库克隆取不到，必须上网查（issue tracker、discussion、邮件列表）；取证过程不可机械化，系统性偏少是预期常态——宁可标 `parity-incidental` 并留一条 Open Question，不虚标 `parity-incidental-relied`。

## 二、证据类别组合与 confidence 推导表（本 skill 约定，无标准可依）

正向需求工程不存在「重建时证据类别组合怎么折算成置信度」这个问题，没有标准可依。下表是本 skill 的原创判据，据实标注为约定，不伪托标准：

| 组合 | confidence | 说明 |
|---|---|---|
| `test+code+doc` | high | 三源一致，最硬 |
| `test+code` | high | 有意锁定且实现一致，缺宣称 |
| `code+doc` | medium | 无测试锁定——重写时无红灯保护 |
| `test+doc`（代码行为相反） | —— | 不是需求，是发现 #1/#2，进冲突处理 |
| `code-only` | medium/low | 过 parity 分类闸门后才可入条款 |
| `doc-only` | low | 可能已漂移，必须代码核实后升级或降为发现 #1 |

推导时按此表机械查表，不要凭手感在 medium/high 之间挑一个更好看的值；`code-only` 落在 medium 还是 low，由 parity 分类结果决定——`parity-contractual` 或有依赖证据的 `parity-incidental-relied` 可到 medium，无依赖证据的 `parity-incidental` 只能是 low 且不得写成条款（按内容项表处理为行为观察附录）。

## 三、三源冲突处理规则

任何两源冲突（doc vs code、test vs doc、test vs code）→ 不得择一写成需求。处置：

1. 落为「尖锐发现清单」条目（发现 #1 文档承诺未实现/与实现相反，或发现 #2 测试与文档矛盾，判定方式见 SKILL.md「尖锐发现清单」表）。
2. 同时写进对应 Candidate Requirement Block 的 `## Open Questions`，注明冲突双方各自的出处（`file:line` 与文档段落/版本）。
3. 不得凭个人判断择一采信，也不得含糊其词各打五十大板——冲突本身就是可交付的价值，写清楚冲突是什么、双方各自的证据是什么就够了。

规则逐字：**冲突必须人裁，skill 不代答。**

三源一致时不算冲突，直接按第二节的组合表推导 confidence；两源一致、第三源缺席（该证据源本身不存在），同样按组合表处理，不要因为"没有第三源"就当作冲突。

## 四、Source Trace 钉版本

格式统一为 `<upstream>@<baseline>:<file>:<line>`，与 SKILL.md「证据纪律」一节一致（不使用设计草稿阶段出现过的 `<baseline-commit>` 变体）：

- `<upstream>`：源项目标识，用于和后续重写仓库自身的产物区分——本 skill 的证据永远指向外部项目，不是本地重写仓库。
- `<baseline>`：Step 0（定重写语义）钉死的 parity 基线版本（tag 或 commit）。
- `<file>:<line>`：源项目内的相对路径与行号。

**基线是硬要求，不是建议**：

- 基线在 Step 0 一旦确定即锁定，全篇所有 Source Trace 条目引用同一个基线，不得中途切换——parity 对照必须可复现，基线混用会让整份产出失去可核验性。
- 行号会随上游后续提交漂移。architecture-reconstruction 对此的纪律是：`file:line` 是「事实」的唯一凭据，行号会漂移，所以同时记录依据的 commit（转述，非引用其原句）；本 skill 把这条从建议升为硬要求：缺失基线的 trace 条目不合格，不得计入 `confidence: high` 的凭据。
- 复核时若按基线内容定位、发现行号已经对不上，视为该条 trace 失效——按上下文重新定位并更新行号，不得保留旧行号继续冒充有效证据。
- 若中途发现基线选错（例如目标重写的版本变了），必须对受影响的证据重新走一遍核实流程，不得只把版本号文字替换一下就当作已更新——不同 commit 之间同一行号不保证对应同一行为。

**探针测试结果的 trace 条目写法**：探针（SKILL.md「验证」第 ③ 项）是把 `code-only` 断言升格为可验证事实的唯一机械手段，但它的产出是「在基线构建上跑某条命令得到某个可观察结果」，**没有对应的上游 `file:line`**，套不进上面的格式。写法约定如下：

```
- 【事实·探针】[<证据类别组合>] <在基线上执行的完整命令> → <观察到的结果>
                （基线构建：<upstream>@<baseline>；被验证的代码位置 <upstream>@<baseline>:<file>:<line>）
```

三条要求：命令必须是可原样重跑的完整命令（不是「我试了一下」）；必须写明它验证的是哪一处代码位置，那一处仍按标准格式带基线；证据类别组合不因探针而改变（`code-only` 探针通过后仍是 `code-only`，改变的是它从【推断】升为【事实】、confidence 可据 parity 分类结果取到 medium）。探针**不能**把 `code-only` 变成 `test+code`——上游没有为它写测试这一事实没有改变，重写时依然没有上游红灯保护。
